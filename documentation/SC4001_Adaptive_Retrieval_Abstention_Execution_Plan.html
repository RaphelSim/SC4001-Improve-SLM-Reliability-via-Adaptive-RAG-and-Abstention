SC4001 Detailed Execution Plan

Research Question: Can adaptive retrieval and abstention improve the reliability of a small language model when retrieved evidence is incomplete?

1. Exact Project Focus

Main research question:
Can adaptive retrieval and abstention improve the reliability of a small language model when retrieved evidence is incomplete?

This project is specifically about reliability under incomplete retrieval. The central problem is:

A question requires multiple pieces of evidence.

Initial RAG retrieval returns only part of the required evidence.

What should the SLM do?

1. Detect that the evidence is incomplete.
2. Identify what information is missing.
3. Retrieve again using a targeted follow-up query.
4. Answer only if sufficient evidence is recovered.
5. Otherwise abstain instead of producing an unsupported answer.

The intended behaviour is therefore:

Detect incompleteness Recover missing evidence Answer when supported Abstain when unsupported

Inference cost is not the main research objective. Retrieval count, latency, or token use may be recorded as secondary observations, but the primary outcome is whether unsupported answers are reduced while useful answer coverage is maintained.

2. Main Hypothesis

Hypothesis:
Compared with standard RAG, an SLM equipped with evidence-sufficiency checking, adaptive follow-up retrieval, and abstention will produce fewer unsupported answers when the initially retrieved evidence is incomplete.

The expected trade-off is:

Standard RAG:
Incomplete evidence → still answers → higher risk of unsupported answer

RAG + Abstention:
Incomplete evidence → detects insufficiency → refuses
Reliable, but may lose answer coverage

Adaptive RAG + Abstention:
Incomplete evidence → detect → retrieve missing evidence
                      ↓
                recovered? yes → answer
                           no  → abstain

Goal:
Lower unsupported-answer rate while preserving more answer coverage than simple abstention.

3. Systems to Compare

System Detects Insufficient Evidence? Retrieves Again? Can Abstain? Purpose
A. Standard RAG No No No Baseline. Always answers from initially retrieved evidence.
B. RAG + Abstention Yes No Yes Measures whether simply refusing on incomplete evidence improves reliability.
C. Adaptive Retrieval only Yes Yes No Measures whether follow-up retrieval can recover missing evidence, but still forces an answer.
D. Adaptive Retrieval + Abstention Yes Yes Yes Main proposed system. Recover evidence when possible; otherwise abstain.

This 4-system setup allows the team to separately measure the contribution of adaptive retrieval and abstention.

5. Recommended Dataset and Evidence Construction

Primary dataset: HotpotQA

Use HotpotQA because many questions require multiple supporting facts. This lets the team deliberately construct incomplete evidence conditions in a controlled manner.

For each question, preserve:

  • Question ID
  • Question text
  • Gold answer
  • Gold supporting documents / supporting facts
  • Candidate paragraphs

Evidence conditions

Condition Construction Expected Reliable Behaviour
Complete evidence All required gold supporting evidence is included. Answer.
Partially incomplete One required supporting item is removed. Detect insufficiency → retrieve missing evidence → answer if recovered.
Fully incomplete All required supporting evidence is removed. Attempt recovery; abstain if support remains unavailable.
Distractor-heavy (optional) Correct support is mixed with several irrelevant passages. Ignore irrelevant context and avoid unsupported conclusions.

7. Parallel Work Split for 3 Members

Member 1 — Dataset, Retrieval, and Incomplete-Evidence Construction

Research role: create the evidence environment in which incomplete retrieval can be studied reliably.

  • Load HotpotQA and preserve gold supporting facts.
  • Create fixed development, validation, and test splits.
  • Implement paragraph embeddings.
  • Implement Top-k dense retrieval.
  • Measure supporting-evidence Recall@k.
  • Create complete, partially incomplete, and fully incomplete evidence conditions.
  • Optionally create distractor-heavy conditions.
  • Cache initial retrieval results.

Required interface:

  • initial_retrieval.jsonl
  • Recall@k results

Member 2 — Evidence Sufficiency Detection and Abstention

Research role: determine whether the SLM can recognise that current evidence is insufficient and avoid unsupported answering.

  • Set up the SLM.
  • Implement Standard RAG baseline.
  • Design the evidence-sufficiency prompt.
  • Use structured JSON output.
  • Implement the RAG + Abstention system.
  • Evaluate:
    • True sufficient → correctly answer
    • True incomplete → correctly detect insufficiency
    • False sufficiency
    • False insufficiency

Required interface:

assess_evidence(question, evidence) -> {
  "status": "SUFFICIENT" | "NEED_MORE_EVIDENCE",
  "missing_information": "...",
  "search_query": "..."
}

Main outputs:

  • slm.py
  • sufficiency.py
  • abstention.py
  • Sufficiency detection metrics

Member 3 — Adaptive Evidence Recovery and Overall Evaluation

Research role: determine whether the system can recover missing evidence before deciding to abstain.

  • Consume the SLM's NEED_MORE_EVIDENCE decision.
  • Use the generated search_query for a second retrieval.
  • Merge and deduplicate evidence.
  • Re-run the sufficiency check.
  • Implement:
    • Adaptive Retrieval only
    • Adaptive Retrieval + Abstention
  • Measure missing-evidence recovery rate.
  • Build shared evaluation scripts.
  • Produce final result tables and plots.

Controller logic:

evidence = retrieve(question)

decision = assess_evidence(question, evidence)

if decision["status"] == "SUFFICIENT":
    return answer(question, evidence)

new_docs = retrieve(decision["search_query"])
evidence = merge_and_deduplicate(evidence, new_docs)

decision = assess_evidence(question, evidence)

if decision["status"] == "SUFFICIENT":
    return answer(question, evidence)

return ABSTAIN

8. How the 3 Members Can Work Independently

  1. Agree on interfaces first. Every module must have fixed input/output formats before implementation.
  2. Use mock data. Member 2 can test sufficiency using manually prepared evidence. Member 3 can test the controller using fake retriever/model outputs.
  3. Use cached JSONL handoffs. No person needs another person's code running continuously.
  4. Create a common development set of 20–30 questions. Everyone tests against the same examples.
  5. Integrate early. Connect minimal working versions before polishing individual modules.

10. Core Metrics

A. Answer correctness

  • Exact Match (EM)
  • Answer F1

B. Evidence-sufficiency detection

  • Accuracy
  • Precision
  • Recall
  • F1

C. Retrieval quality

  • Supporting-evidence Recall@k

D. Missing-evidence recovery

Recovery Rate:
Among cases where initial evidence is incomplete, what fraction successfully recover the missing gold support after adaptive retrieval?

E. Reliability

  • Unsupported Answer Rate: how often the system answers even though available evidence is insufficient.
  • Correct Abstention Rate: how often the system correctly refuses when support remains insufficient.
  • Answer Coverage: how often the system is able to provide an answer instead of abstaining.

The main trade-off should be analysed as:

Reliability ↑
Unsupported answers ↓
while
Useful answer coverage remains high

12. Development / Validation / Test Protocol

  1. Development set: used for debugging and prompt construction.
  2. Validation set: used to choose Top-k, prompt wording, controller rules, and evidence formatting.
  3. Test set: untouched until the system is frozen.
  4. Use the same SLM, quantisation, decoding settings, and runtime for all final systems.
  5. Do not change prompts after viewing final test results.
  6. Cache all final outputs for reproducibility.

15. Failure Cases to Analyse

  • False sufficiency: model believes incomplete evidence is enough and answers anyway.
  • False insufficiency: model asks for more evidence although support is already sufficient.
  • Wrong missing-information diagnosis: model identifies the wrong fact as missing.
  • Poor follow-up query: the generated query does not target the missing evidence.
  • Good query but retrieval failure: query is appropriate, but the retriever does not recover the gold support.
  • Evidence recovered but answer still wrong: retrieval succeeds but reasoning fails.
  • Over-abstention: model refuses despite having sufficient support.

16. Scope Control

  • Do not fine-tune the SLM for the initial project.
  • Do not make inference cost the main objective.
  • Do not add GraphRAG to the core experiment.
  • Keep contradiction detection as optional future work.
  • Use one primary dataset first.
  • Use one SLM family for the main comparison.
  • Limit adaptive retrieval to one follow-up round.

17. Optional Extensions

  • Compare 1.7B vs 4B SLMs on evidence-sufficiency detection.
  • Add contradiction-aware handling after the core project is complete.
  • Add a reranker to test whether better evidence selection reduces false insufficiency.
  • Test robustness to increasing distractor evidence.
  • Record latency/tokens only as secondary engineering metrics.

18. Final Expected Contribution

Problem: Standard RAG can still produce unsupported answers when required evidence is missing.

Method: detect evidence insufficiency, generate a targeted follow-up query, retrieve missing evidence, and abstain if sufficient support still cannot be obtained.

Research question answered: does combining adaptive retrieval and abstention make an SLM more reliable under incomplete evidence?

Main evidence of improvement: lower unsupported-answer rate, high correct-abstention rate, successful missing-evidence recovery, and useful answer coverage.

This version is intentionally centred only on incomplete evidence, adaptive recovery, abstention, and reliability.
